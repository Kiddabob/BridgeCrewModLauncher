Launcher architecture and milestones
====================================

The launcher uses .NET 10 and native WinUI 3. The separate PHP 8.4/SQLite service
provides persistent accounts, publishing, friends and launcher rooms. Its public
API and private data live in isolated folders on existing Hostinger hosting.
The future game plugin must target Bridge Crew's old Unity/Mono runtime and is
not included. No game installation is altered or launched by this milestone.

Host/guest flow
---------------
A host signs in, selects an immutable published pack, chooses its declared
edition/build, reviews each mod and subscribes, then opens a launcher room.
A guest finds the room publicly, through an accepted friendship or by explicit
invitation, reviews its pack, subscribes to its own edition's verified payloads,
and joins the launcher room. Readiness rechecks the reviewed subscription.

The server checks identity, visibility, blocks, invitations, capacity, pack
lock and room revision. Rooms expire after 120 seconds without host renewal;
active clients heartbeat every 30 seconds. A guest cannot keep an absent host's
room alive. Existing unexpired membership can be restored after app restart.
Every room reports gameConnected=false and status=launcher-room-only.

Game connection remains a separate later component: a qualified plugin must
advertise the actual game room, bind that room to the pinned pack, and confirm
the game handshake before the launcher may report in-game joining. A cached
pack, backend room or ready flag is not evidence of entering the game.

Pack rules
----------
The manifest pins mod versions, dependencies, load order, descriptions, shared
files, Meta/Steam variants and declared builds. Canonical SHA-256 locks the
whole manifest. PHP and .NET lock interoperability is tested with Unicode,
HTML-sensitive characters and literal escape sequences. Clients revalidate all
metadata and selected payload sizes/hashes. Cached files alone do not replace
consent to a particular manifest. Online caches are scoped to their service.

Publishers require owner approval. Files are uploaded to private storage and
verified before immutable publication; a publisher can only reference owned
payloads and cannot take another publisher's pack ID. Publisher account identity
is shown separately from mod author text. Owner moderation can hide releases
or disable accounts. It cannot revoke files already downloaded to a client.

Accounts and hosting
--------------------
Passwords use Argon2id. Sessions and recovery secrets are stored hashed; reset
rotates the recovery secret and revokes prior sessions. Authentication changes
are checked inside database transactions. API requests use HTTPS; metadata
and uploads have size/rate/storage caps. API clients refuse redirects. The
native app encrypts saved sign-in state for its Windows user and service URL.

SQLite and payloads are outside public_html. Only BridgeCrew's .htaccess selects
PHP 8.4. Other site files, PHP settings, database configuration and cron jobs
are preserved. See Backend/README.txt for concrete paths, limits and commands.
No daemon, paid additional hosting or external database service is required.

App updates
-----------
Velopack runs before WinUI startup. The installer owns its replaceable current
folder, shortcuts and uninstall registration; user data lives separately.
GitHub releases supply the app update feed. Download/apply/restart are separate
operations. The native window explicitly registers its taskbar identity and
Starfleet/spanner relaunch, small and large icons; owned shortcuts reference a
content-named icon. Missing shortcuts stay missing; taskbar pins are unchanged.
The user confirmed the actual taskbar appearance for 0.2.4 on 2026-10-17.

Deferred

After qualification, implement game-room advertisement/handshake, the in-game
Modded Crew menu, activation/rollback and controlled restart/reconnect. Keep
SDK authoring tools separate and base them on tested engine/plugin contracts.
